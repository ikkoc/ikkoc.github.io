实际优化

向量化访存

向量化加载 packed_weights

单字节 load，效率差。GPU 更适合 4B / 8B 对齐访问。
需注意，主机端对 packed buffer 做 4 字节对齐补零，避免最后一个 uint32 读取越界。

读取方式改为 16B 向量化

kernel 参数从 const uint32_t* 改为 const uint4*
每线程处理 1 个 16B word（32 个权重），total_words = ceil(total_bytes / 16)
读取 16B 后用 #pragma unroll 在寄存器里拆 16 个 byte，再拆成 32 个 4-bit 索引
参数只读一次

对应这 32 个权重只计算一次 block_id/group_id
只读一次 absmax2/absmax_q/code2/offset，得到 real_absmax，后面 32 个权重复用
写回向量化

每个byte 生成 2 个 bf16，打包成 1 个 uint32
16 个 uint32 组成 4 个 float4，一次写回 8 个 bf16
尾部不足 32 权重时走标量写回，避免越界
主机侧对齐与网格调整
packed buffer padding 改为 16B 对齐
cudaMalloc/cudaMemcpy 使用对齐后的大小
grid 上限按 total_words 而不是 total_bytes 计算

此外，精简写回：跳过 float4 强转

既然已经拼接好了 uint4，直接用 uint4 类型的指针写回即可。GPU 并不在乎你存入的是 float 还是 uint，只要它是 128 位的。当告诉 GPU 要执行一个存储（Store）操作时，硬件只需要知道两件事：
起始地址（Starting Address）： 数据要写到哪？
位宽（Bit Width）： 这一趟搬多大的数据（32位、64位还是 128位）？
当定义一个 uint4 变量并写回时，CUDA 编译器（NVCC）会生成一条类似 STG.E.128 (Store Global 128-bit) 的汇编指令。这条指令不管这 128 位里装的是 8 个 bfloat16、4 个 float，还是 16 个 char。它只负责把寄存器里的 128 个比特流，原封不动地拍到对应的显存地址上。

按题目要求回退线程粒度

题目要求的是 Packed Store：每个线程一次只处理两个 4-bit 索引，也就是读取 1 个 packed byte，算出 2 个 bf16 后，打包成 1 个 uint32_t，一次性写回全局内存。
而我前一版做的是：kernel 输入改成 const uint4*，每个线程先读 1 个 uint4，也就是 16 个 byte
16 个 byte 对应 32 个 4-bit 索引
线程内部虽然也调用了 pack_pair_to_u32(v1, v2)
但那只是线程内部的中间步骤，最终是把 16 个 uint32 再组成 4 个 uint4 写回
也就是说，之前那版本质上是：
每线程处理 16 个 packed byte
每线程解码 32 个 4-bit 索引
每线程最终写 4 个 uint4
这不等于题目要求的：
每线程处理 1 个 packed byte，每线程解码 2 个 4-bit 索引，每线程最终写 1 个 uint32_t。所以这里重新改回严格按题目要求实现。

同时 host 端的 grid 计算也要跟着改回按 total_bytes 来算，而不是按 total_words 算。因为现在一个线程对应一个 packed byte，不再是一个线程对应一个 uint4。

这版的好处是题意完全对齐，线程粒度、处理粒度、写回粒度三者一致。缺点也很明显，性能会比之前那个“每线程吞 16 个 byte”的版本低一些。

  • 改善 packed_weights 和 output store 的访存效率；

同时也要说明一点：这个 kernel 有大量 unpack、整数地址计算、shuffle、convert、pack，传统 FP roofline 只统计 FADD/FMUL/FFMA 这些浮点操作，所以 AI ≈ 0.42 FLOP/byte 是 FP32 roofline 口径下的算术强度，不代表“所有指令工作量 / byte”。不过用它判断 compute-bound 还是 memory-bound，已经足够明确。

3. 这一轮实验的结论

这两个实验和 roofline 结论是互相印证的：

  • 移位替代除法能减少整数路径开销，所以有小收益；
  • 简单向量化访存没有稳定收益，因为主限制仍然是 DRAM roof；
  • 后续如果继续优化访存，需要更精确地减少 DRAM bytes 或重排 scale metadata 的依赖链，而不是只把单线程处理粒度放大。

补充：继续用 NCU 验证 LUT 路径和线程组织

前面我写到 shared LUT 在 benchmark 里比直接查 constant 更快，但如果只停在“benchmark 更快，所以保留”其实还是有点虚。

因为 constant memory 这件事很容易让人产生一个直觉：表只有 16 项，又是只读数据，那放 constant 不就应该更优吗？

但这次我专门重新跑了一轮 NCU，想把这件事看得更细一点。结论是：这个 kernel 里，shared LUT 更快不是偶然，而且原因也能从 NCU 里看出来。

1. shared LUT vs constant direct

我这里对比的是两版：

  • shared 版：先把 NF4_LUT[16] 从 constant 搬到 __shared__，后续查表走 LDS
  • constant direct 版：去掉 shared staging，后续直接 LDC 查 constant

为了避免别的变量混进来，我只改 LUT 路径，不改其他逻辑。两版输出一致。

benchmark 上：

  • shared LUT: 1.774 ms
  • constant direct: 1.799 ms

单看 benchmark，差距不算特别夸张；但 NCU 给的信息更有意思。

2. 从 NCU 看，constant direct 输在哪

shared 版的关键信息大概是：

  • DRAM Throughput: 84.79%
  • Memory Throughput: 834.9 GB/s
  • eligible warps per scheduler: 1.09
  • warp latency per issued instruction: 28.79
  • long scoreboard: 19.39
  • short scoreboard: 1.24
  • mio throttle: 0.38

constant direct 版：

  • DRAM Throughput: 77.13%
  • Memory Throughput: 755.4 GB/s
  • eligible warps per scheduler: 0.53
  • warp latency per issued instruction: 30.96
  • long scoreboard: 13.08
  • short scoreboard: 8.78
  • mio throttle: 3.71

这里最关键的不是某一个 throughput 数字，而是 stall 结构变了。

shared 版虽然也不是没有 stall，但它主要还是卡在 long scoreboard，也就是“等比较长的内存依赖链返回”。

constant direct 版的问题是：

  • short scoreboard 明显更高
  • mio throttle 明显更高
  • eligible warps 明显更少

也就是说，constant direct 并没有把这 16 项 LUT 变成“完全免费”的广播访问。

原因也不难理解：NF4 的索引在 warp 内并不 uniform，同一个 warp 里不同线程查到的表项经常不一样。这种情况下，constant memory 那种“全 warp 同地址广播”的理想场景并没有真正成立。结果就是，直接查 constant 会把压力更多打到 MIO / scoreboard 这条路径上，调度器手里能随时发射的 warp 反而更少。

而 shared 版虽然多了一次 64B 的 shared staging 和一个 __syncthreads()，但后续查表都变成了 shared load，整体上反而更顺。

所以到这里，我对 shared LUT 的判断就比之前更明确了：

不是“benchmark 恰好快了一点，所以姑且保留”，而是：

在这个 kernel 里，NF4 LUT 的访问模式并不适合把 constant memory 当成理想广播来理解。NCU 显示 constant direct 会显著抬高 short scoreboard 和 mio throttle，降低 eligible warps；shared LUT 通过一次 preload 把后续查表改成 shared load，整体 kernel duration 更低，所以应当保留 shared LUT。

这个结论我现在是比较确信的。

3. 继续追问：如果 LUT 不是主矛盾，那还能不能靠线程组织再抠一点

看到前面的 NCU 之后，我的直觉是：

这个 kernel 的主瓶颈还是全局访存等待，而不是 LUT 本身。

于是我又做了一个 mainla_v2 的尝试，思路是：

  • 不改变题目要求
  • 仍然保持“每线程处理 1 个 packed byte，解两个 4-bit，打包成 1 个 uint32_t 写回”
  • 但把线程映射重组为 1 warp -> 1 quant block

因为这里 blocksize=64，所以一个 quant block 恰好对应 32 个 packed bytes，也正好对应一个 warp。这个映射从概念上看是很自然的：

  • lane 0 读 absmax_q / absmax2 / code2
  • 用 __shfl_sync 广播 real_absmax
  • 一个 warp 的 32 个线程各自处理这个 quant block 里的一个 packed byte

我当时预期这会带来两个收益：

  1. block_id / group_id 相关地址计算更规整
  2. scale 复用更显式

4. 结果：原始 v2 反而更慢

先说结果，原始 v2 并不好：

  • mainla: 1.77765 ms
  • mainla_v2: 1.83308 ms

NCU 一看就知道问题在哪：

  • registers per thread: 24 -> 34
  • eligible warps: 1.10 -> 0.70
  • warp latency: 28.65 -> 36.26
  • long scoreboard: 19.41 -> 28.24

也就是说，我这个第一版 v2 虽然在映射关系上看起来更“工整”，但实际上引入了更多 live range 和更多状态，寄存器压力上去了，最后反而让调度器更难受。

所以这一步让我意识到一个很具体的问题：

线程组织“看起来更符合数据结构”不等于一定更快。只要寄存器和依赖链被拉长，原本想省下来的那点地址计算，很可能立刻就被吞回去了。

5. 既然 v2 思路不完全错，那就继续把它写紧一点

虽然第一版 v2 慢了，但我还是想确认一下：

到底是 warp-per-block 这个思路本身没收益，还是我第一版实现写得太松了。

于是我继续在 v2 上做了几轮更小心的尝试，只动 v2，不碰当前 mainla。

5.1 对 v2 做 blocksize=64 特化

因为当前实际数据就是：

  • blocksize = 64
  • group_size = 256

所以我把 v2 进一步专门化成 bs64 版本：

  • 去掉 bytes_per_block == 32 的运行时分支
  • num_blocks 改成位运算
  • byte_idx 改成移位加 lane
  • kernel 参数里不再传 blocksize

这个版本我本来希望能明显回收一部分开销，但 benchmark 上提升并不大。

5.2 扫一轮 blockDim

接着我系统扫了一轮 block size，大概测到：

  • blockDim=64: 1.83107 ms
  • blockDim=96: 1.82888 ms
  • blockDim=128: 1.82905 ms
  • blockDim=192: 1.82299 ms
  • blockDim=256: 1.83100 ms
  • blockDim=224: 1.89579 ms
  • blockDim=320: 1.92249 ms
  • blockDim=512: 1.85896 ms

这里面最好的点大概落在 192 附近。

这个结果也挺符合直觉：warp-per-block 这种写法对 CTA 里 warp 的组织方式更敏感，256 并不天然就是最优值。

5.3 再试寄存器上限

因为之前 v2 最明显的问题就是寄存器太多，所以我又试了 -maxrregcount：

  • -maxrregcount=24: 1.84260 ms
  • -maxrregcount=28: 1.82965 ms
  • -maxrregcount=32: 1.82898 ms

放在 blockDim=192 上再测：

  • blockDim=192, -maxrregcount=28: 1.83714 ms
  • blockDim=192, -maxrregcount=32: 1.82237 ms

这里真正有效的一组配置是：

  • bs64 特化
  • blockDim=192
  • -maxrregcount=32

6. v2 最终有没有变好

有，但幅度非常有限。

把原始 v2 和调过之后的最好版本比一下：

  • 原始 v2: 1.83308 ms
  • 最优 v2: 1.82237 ms

也就是说，大概只提升了 0.6%

NCU 里也能看到一点对应变化：

  • gpu__time_duration.sum: 1.857 -> 1.839 ms
  • dram throughput: 798.2 -> 806.2 GB/s

但这个提升本质上更像是：

“把我第一版 v2 自己引入的多余开销收回了一点”

而不是说 warp-per-block 这个方向突然带来了一个新的主收益点。

更有意思的是，虽然最优 v2 把寄存器数压到了 17，但：

  • eligible warps 还是不高
  • warp latency 依然偏高
  • long scoreboard 依然高

所以瓶颈并没有本质变化。它仍然是一个在等全局访存返回的 kernel。

7. 这几轮尝试之后，我现在的结论

已经验证清楚的事：

  1. shared LUT 应该保留，不建议改回 constant direct
  2. 这个 kernel 的主瓶颈仍然是主数据流上的全局访存等待
  3. 在题目要求的线程粒度下，单纯重组 warp 映射，收益非常有限
  4. mainla_v2 这条线即使继续打磨，也更像是在“消除自己引入的额外开销”，不是在打开一个新的大收益空间
